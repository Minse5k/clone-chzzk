# 여러 서버 인스턴스는 상태를 PostgreSQL·Redis·공유 볼륨에 두고, 라이브는 하트비트로 지킨다

과제 5에서 서버를 여러 인스턴스로 띄우고 부하에 따라 늘리고 줄인다. 요청은 어느 인스턴스로든 갈 수 있고 인스턴스는 언제든 사라질 수 있으므로, 인스턴스 안에는 연결(WebSocket, ffmpeg 프로세스) 말고는 상태를 두지 않는다.

- **DB → PostgreSQL**: SQLite 파일은 한 컨테이너 안에 있어 다른 인스턴스가 쓸 수 없고, 공유 볼륨에 둬도 동시 쓰기가 한 파일 잠금에 몰린다. 모든 인스턴스가 PostgreSQL 하나를 함께 쓴다. 과제 4까지의 스키마를 Postgres용으로 다시 만들었다(SQLite 데이터는 옮기지 않는다). 저장 총량 확인과 동시 라이브 수 확인처럼 "세고 나서 쓰는" 일은 트랜잭션 advisory lock으로 인스턴스 사이에서도 줄을 세운다. 후원 확정의 `status='pending'` 조건부 갱신은 그대로 여러 인스턴스 사이의 중복 확정도 막는다.
- **로그인 → JWT + DB 폐기 목록**: 토큰은 상태가 없어 모든 인스턴스가 같은 `JWT_SECRET`만 쓰면 된다. 로그아웃한 토큰 목록은 DB에 있다.
- **실시간 알림·제어 신호 → Redis Pub/Sub**: 댓글 WebSocket과 송출 연결은 한 인스턴스에 붙는다. 댓글·후원 알림(`chzzk:broadcast:{id}`)과 방송 삭제·송출 종료 요청(`chzzk:control`)을 Redis로 보내고, 모든 인스턴스가 구독해 자기 연결에 나눈다. 알림은 놓쳐도 되는 신호다(웹은 다시 연결할 때 목록을 새로 받는다). 놓치면 안 되는 상태(방송 종료)는 DB에 먼저 쓰고 신호는 그 뒤에 보낸다.
- **녹화본·라이브 HLS 조각 → 공유 볼륨**: 송출받는 인스턴스의 ffmpeg가 쓴 조각을 다른 인스턴스도 서빙하고, 송출받던 인스턴스가 죽으면 다른 인스턴스가 남은 조각으로 녹화본을 만든다. 녹화본은 기존처럼 OCI Object Storage에 둘 수도 있다.
- **라이브 상태 → 하트비트**: 전에는 서버가 시작할 때 라이브 중인 방송을 모두 종료했다. 인스턴스가 여럿이면 새 인스턴스가 뜰 때마다 다른 인스턴스의 라이브가 끝나 버린다. 송출받는 인스턴스가 몇 초마다 `ingest_heartbeat_at`을 갱신하고, 모든 인스턴스가 하트비트가 `LIVE_HEARTBEAT_TIMEOUT_SECS` 넘게 끊긴 라이브만 조건부 갱신으로 종료한다. 기록과 비교 모두 DB 시계(`now()`)를 쓴다. 동시 라이브 수는 인스턴스마다 세던 세마포어 대신 DB의 라이브 방송 수로 센다.

오케스트레이터는 Docker Compose, 스케일러는 직접 만든다(`apps/autoscaler`). 로컬에 Kubernetes가 없고, 과제가 클라우드 배포를 요구하지 않으며, 줄일 때 "송출을 받고 있지 않은 인스턴스만 고른다"는 규칙을 Compose의 `--scale`(번호가 큰 컨테이너부터 지움)이나 HPA로는 바로 표현할 수 없기 때문이다. 늘리기는 `docker compose up --scale`로, 줄이기는 각 인스턴스의 `/healthz`를 보고 송출이 없는 컨테이너를 골라 `docker stop`(정상 종료)으로 한다.

## Consequences

- 송출 연결 자체는 인스턴스를 옮겨 가지 못한다. 송출받던 인스턴스가 죽으면 그 방송은 하트비트 시간 뒤 종료되고 남은 조각이 녹화본이 된다. 정상 종료(SIGTERM)라면 그 인스턴스가 송출을 이유와 함께 끝내고 녹화본까지 만든 뒤 내려간다.
- 인스턴스가 내려갈 때 댓글 WebSocket은 닫히고, 시청 화면은 잠시 뒤 다른 인스턴스로 다시 연결한다.
- `REDIS_URL`이 없으면 알림을 프로세스 안에서만 전한다. 인스턴스 1개(로컬 개발, 대부분의 테스트)는 Redis 없이 돈다.
- 통합 테스트는 실제 PostgreSQL(테스트마다 새 데이터베이스)과 Redis를 쓰고, 같은 DB·Redis·디렉터리를 쓰는 서버 두 개를 띄워 인스턴스 사이의 동작을 검사한다.
