# 후원은 서버의 결제 승인 확인으로만 확정하고, 상태 조건부 갱신으로 한 번만 적립한다

후원 결제는 토스페이먼츠 결제창(테스트 키)을 쓴다. 결제창이 성공 주소로 돌아왔다는 사실, 그 주소의 쿼리 값, 웹훅 본문은 모두 브라우저나 네트워크에서 바뀔 수 있으므로 후원을 확정하는 근거로 쓰지 않는다. 서버는 주문을 만들 때 받는 사람(방송 소유자)과 금액을 정해 저장하고, 승인 확인 요청이 오면 먼저 요청 금액을 저장된 주문 금액과 대조한 뒤 결제 승인 API(`POST /v1/payments/confirm`)를 직접 부른다. 응답의 상태가 `DONE`이고 주문번호와 총액이 주문과 같을 때만 확정한다. 웹훅은 본문의 `paymentKey`로 결제 조회 API를 불러 같은 대조를 거친 뒤 같은 확정 경로를 탄다.

확정은 `UPDATE donations SET status='confirmed' … WHERE order_id=? AND status='pending'`이다. 영향 행이 1인 요청만 새 후원으로 보고 알림을 보낸다. 같은 승인 확인이 다시 오거나(새로고침, 재시도), 웹훅이 여러 번 오거나, 둘이 동시에 와도 두 번째부터는 영향 행이 0이라 다시 적립되지 않는다. `payment_key` 유일 제약으로 같은 결제가 다른 주문에 확정되는 것도 막는다. 결제 서비스 호출을 DB 트랜잭션으로 감싸지 않아도 되는 이유는 승인 API 자체가 같은 결제를 두 번 승인하지 않기(`ALREADY_PROCESSED_PAYMENT`) 때문이고, 그 경우 서버는 결제를 조회해 같은 확정 경로를 탄다.

주문과 확정 후원은 한 표(`donations`)에 상태로 구분해 둔다. 후원 내역과 합계는 `confirmed`만 센다.

## Consequences

- 결제 서비스는 `TOSS_API_BASE`로 주소를 바꿀 수 있어, 통합 테스트는 같은 응답 형식의 가짜 서버로 승인·거절·금액 불일치·중복 승인을 재현한다.
- 승인된 결제가 주문과 맞지 않으면(금액·주문번호) 후원을 확정하지 않고 오류 로그를 남긴다. 결제 취소(환불) API는 이번 단계 범위 밖이라 사람이 확인해야 한다.
- 후원 내역은 돈이 오간 기록이므로, 확정된 후원이 있는 방송은 삭제할 수 없다.
- 토스페이먼츠 결제 상태 웹훅에는 서명이 없어, 본문 대신 조회 API 결과를 믿는다.
