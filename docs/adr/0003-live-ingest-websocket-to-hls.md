# 라이브 송출은 브라우저 녹화 조각을 WebSocket으로 받아 서버가 HLS로 바꾼다

휴대폰 브라우저가 카메라·마이크 스트림을 MediaRecorder로 1초 단위 조각으로 만들어 WebSocket으로 서버에 보낸다. 서버는 송출마다 ffmpeg 프로세스 하나에 조각을 그대로 흘려 넣고, ffmpeg가 H.264/AAC로 다시 인코딩해 2초 단위 HLS 조각과 재생 목록을 만든다. 시청자는 HLS로 본다(hls.js, iOS Safari는 기본 재생). 송출이 끝나면 같은 HLS 조각을 다시 인코딩 없이 mp4로 묶어 녹화본 저장소에 넣는다.

WebRTC(WHIP/WHEP, 예: mediamtx)는 지연이 1초 미만이지만, 별도 미디어 서버와 UDP 포트·NAT 설정이 필요하고 녹화본을 만들려면 그 서버와 앱을 다시 이어 붙여야 한다. ffmpeg 없이 WebSocket으로 조각을 시청자에게 그대로 중계하는 방식(MSE)은 가장 단순하지만, 중간에 들어온 시청자가 키프레임 없는 조각부터 받게 되고 iOS의 송출·시청 형식이 달라 호환성이 깨진다. 3~6초 지연을 받아들이는 대신, TCP(HTTPS) 하나로 모든 기기에서 송출·시청되고 중간 입장과 녹화본이 자연스럽게 해결되는 쪽을 골랐다.

## Consequences

- 서버(와 배포 이미지)에 ffmpeg가 필요하다. 없으면 녹화방송 기능은 그대로 쓰고 송출만 거부한다.
- 인코딩이 VM CPU를 쓴다. 동시 라이브 방송 수를 `MAX_LIVE_BROADCASTS`로 제한한다.
- 송출 연결의 수명이 곧 라이브 방송의 수명이다. 별도 종료 API나 송출 키가 없어 로그인 없이도 남이 내 방송을 끌 수 없다.
- 라이브 HLS 조각은 서버 로컬 디스크(`LIVE_DIR`)에 두고 서버가 직접 서빙한다. 녹화본만 녹화본 저장소(local/OCI)로 간다.
- 같은 WebSocket 수집 경로를 다음 단계의 데스크톱 송출 앱도 쓸 수 있다.
- 휴대폰 브라우저는 보안 출처(HTTPS)에서만 카메라를 허용하므로, 로컬 확인은 HTTPS 터널, 배포는 HTTPS가 필요하다.
